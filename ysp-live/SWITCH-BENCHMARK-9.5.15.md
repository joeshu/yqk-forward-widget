# 原版与 9.5.14 / 9.5.15 换台路径对照

日期：2026-10-18。原版是用户指定的 ysp-live-v9.5.py，文件 SHA-256 记录在 [原始结果](benchmark-switch-9.5.15.json)。当前版固定最高可用画质策略；模拟使用同一媒体主体，不访问真实 CCTV 注册、播放或 EPG 接口。

## 范围与方法

在同一 Linux/Python 环境，三个版本分别加载独立模块。保留真实本地 HTTP Handler、设备前台线程池、防抖、共享刷新和 ensure_channel；只替换实际取源动作与常驻刷新循环。每个场景每版一个请求，用于复现确定性的串行/排队等待，不是统计吞吐或长期网络评测。源文件哈希、Python 与系统信息保存在 JSON。

以下数字是从客户端发出 GET 到读取完播放列表的时间，**不是首次解码画面、音频、CDN 公网带宽或用户播放器换台时间**。

| 模拟场景 | 最初 v9.5 | 9.5.14 | 9.5.15 |
|---|---:|---:|---:|
| 防抖中、设备线程池满、备用取源 300ms | 301.4 ms | 2302.3 ms | 301.9 ms |
| 防抖中、设备线程池满、备用已缓存 | 1.2 ms | 2001.8 ms | 1.4 ms |
| 设备取源 3s、备用取源 300ms | 3301.9 ms | 2302.6 ms | 2001.8 ms |
| 备用缓存过期 180s、刷新取源 300ms | 301.9 ms | 1.1 ms | 301.7 ms |

## 结果解释

- 没有线程池拥堵的普通防抖请求，两版原本就很接近；不是每次换台都固定多 2 秒。
- 设备线程池被其他频道占用时，9.5.14 连“立即防抖返回空”的动作也要先排队，默认前台等待耗尽后才走备用。9.5.15 将这项无上游 I/O 的判断移到入队之前，恢复原版这条路径的速度。
- 当设备源确实慢、备用源也需要取源时，9.5.14 两段前台等待串行相加。9.5.15 首次播放/闲置回台在等待优先源时启动一次共享备用刷新；仍先尝试设备源，预热不选源、不发布低画质。已有设备缓存和原生 4K 不额外预热，连续观看不重复触发。
- 过期备用的场景中，9.5.14 时间很短但返回旧分片 1，是“假快”；原版与 9.5.15 刷新完成后返回新分片 2。修复避免播放器先请求过期 URL，也避免把这一过程误记为冻结故障产生额外冷却。
- 新鲜的设备列表另有真实繁忙线程池回归，确认不排队且保留原设备来源；来源代际变化、故障或过期时不能走快返。
- 两版 JCE 原有最近 15 片及隐藏最后 1 片策略没有改变；普通媒体分片原本已经流式转发，本次没有以缩小播放窗口或降画质换取列表响应速度。

## 复现

先将原版文件保存到本地，再在仓库根目录执行：

```sh
python3 ysp-live/tests/benchmark_switches.py --original /path/to/ysp-live-v9.5.py --output /tmp/switch-results.json
python3 -m unittest discover -s ysp-live/tests -p 'test_*.py'
```

回归包括过期 GET 等待新片、六个请求共享一次刷新、保留 publication/selector/seq、等待超时只标记准备中、暖缓存不取源、刷新槽满时不发旧片和不误记故障、队列拥堵时防抖与设备缓存不等待、4K 路径保护，以及可选预热失败不影响优先来源。完整套件 263 项通过。

# CCTV 网页来源实验版验证

2026-10-19 UTC；Linux、Python 3.12、系统 Chromium、Playwright、FFmpeg。只验证 CCTV-2 手机网页本身，没有切换到央视频或其他来源。

## 实现选择

官方 `live.worker.js` 能在 Node 中加载，但公开播放器初始化未能在本次 Node 环境完成。这不等于可用的 Node 伴生引擎。直接取出的网页原始分片也不能通过普通严格解码检查。

最终实验版使用完整官方页面正常播放，再通过浏览器标准媒体采集和 MediaRecorder 输出 WebM，FFmpeg 重新编码为 H.264/AAC、MPEG-TS HLS，Python 提供本地订阅及媒体路径。代码未移植官方解密算法、提取内容密钥或修改其播放器模块；也不是原始码流透传。该方式有编码开销和额外延迟，不能当作低延迟直连方案。

## 独立单文件真实验证

将 `cctv-web.py` 单独复制到空目录，服务使用本地端口 18768；真实测试的第二次运行设置了 `--idle-timeout 30`，其他媒体参数沿用默认值。

| 检查 | 本轮结果 |
| --- | --- |
| `/all.m3u` | HTTP 200，1 个 CCTV-2 条目，约 0.01 秒，不启动浏览器 |
| 首次 `/cctv2.m3u8` | 两次独立启动分别约 23.24 秒、22.443 秒后返回 HTTP 200 |
| 第一轮两个 TS 分片 | HTTP 200；698,796 字节、1,169,548 字节 |
| 第一轮 ffprobe | H.264 1280×720，AAC 音频 |
| 第一轮 TS 严格解码 25 帧 | `ffmpeg -xerror` 退出码 0，无错误输出 |
| 第二轮直接通过本地 HLS URL 连续解码 10 秒 | 退出码 0，250 帧，无错误输出 |
| HLS 窗口 | 初始窗口从 2 条逐步增长到 6 条，随后媒体序号从 17 推进至 20；旧分片自动淘汰 |
| `/status` | 实际进入 `ready`，音视频两条采集轨道，`media_ready=true` |

初始 8 秒取样的媒体序号均为 0，这是窗口尚未超过 6 条时正常累积；不能只看初期序号就判定冻结。后续 6 条窗口实测序号从 17 推进至 20。此处耗时是列表准备时间，不等于客户端首帧或与电视直播的时间差。

设置 30 秒闲置回收后，停止播放请求，随后观察 `/status` 为 `idle`、`media_ready=false`，本次会话 TS 文件数为 0。

## 离线检查

9 项本地回归通过：本地 HTTP 订阅及 HEAD 不启动浏览器、失败 503、有效媒体会话路径、过期会话 410、媒体文件与近期窗口完整性、路径限制、Host/公网前缀、状态脱敏、非法方法。使用 `-W error::ResourceWarning` 运行，没有未关闭事件循环告警。

GitHub Actions 在 Python 3.10 / 3.12 执行同一套离线测试，不在 CI 中请求直播上游。

## 尚未验证

用户手机/电视播放器、iOS 上运行 Python、其他频道、24 小时播放稳定性、准确直播时延及低性能设备 CPU 消耗。本版只支持运行 Chromium/FFmpeg 的电脑或服务器；手机可以通过局域网作为播放器。没有 EPG、回看、4K 或其他频道功能。

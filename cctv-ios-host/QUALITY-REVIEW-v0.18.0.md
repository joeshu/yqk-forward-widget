# CCTVHost 现状盘点与 v0.18.0 改进记录

日期：2026-10-24

## 项目与验证边界

- 工程使用 Objective-C/UIKit，XcodeGen 描述位于 project.yml，最低系统版本 iOS 15。
- AppDelegate 将 RootViewController 放入导航控制器；主界面已有 CCTV、频道、影视、资源、设置五个入口。
- 仓库的 macOS CI 执行 JS 插件测试、Python 回归、iOS arm64 语法检查、unsigned IPA 构建、IPA 校验和模拟器 UI 冒烟测试。
- 本次环境为 Linux x86_64，未安装 xcodebuild、xcrun 或 iOS Simulator。因此本机不能编译 UIKit 工程、生成 IPA 或执行模拟器 UI 测试；也不能测量真机播放和首帧性能。
- APTV IPA 未在本轮环境中进行可验证的逐页检查；本轮保留 CCTVHost 已有视觉风格，只按任务描述改善导航反馈与状态信息，不声称复刻了 APTV 的未确认细节。

## 改造前基线

在修改前运行：

    cd cctv-ios-host
    python3 -m unittest discover -s Tests -p 'test_*.py' -v

结果为 113 项通过、21 项因需要 macOS Foundation/JavaScriptCore 而跳过，耗时 9.820 秒。运行环境为 Linux x86_64；此耗时只代表回归套件，不代表 App 性能。

源码基线中，服务目录、服务详情、插件页和资源页各自以 1 秒间隔轮询运行状态/重载数据。EPG 自动刷新间隔为 60 秒。重复触发同一订阅源时会取消前一个请求并重新发起。冷启动、首屏可交互时间、频道渲染时间、真实网络刷新时长、内存和真机首帧均未测。

## 本轮改动

1. 服务目录、服务详情、插件页和资源页改为订阅 Python 宿主状态通知，移除上述 1 秒轮询。服务界面将运行时活动和 HTTP 健康结果分别呈现；普通 HTTP 响应不会被标成健康检查通过。
2. 服务详情的手动检测按服务能力区分：有结构化 /health 的资源检查其 ok 字段；内置直播服务尝试解析真实 M3U 并显示有效频道数；未知服务只显示 HTTP 可达状态与状态码。结果附最近 HTTP 响应时间。服务版本只读实际配置字段，缺失时显示“未知”。
3. EPG 页面在退到后台时停表、取消可直接取消的请求并递增请求代次；回到前台时按需刷新。宿主取消官方 EPG 请求并用独立代次拦截过期回调，同时暂停 XMLTV 网络任务。前台仍处于起播优先窗口时继续暂停 EPG 工作，避免抢占切台资源。
4. 同一个完整订阅 URL 的并发刷新合并为进行中的请求；不同路径、查询参数仍各自独立。订阅卡片显示最近成功刷新时间，并提供单源滑动刷新和长按菜单刷新。删除前显示对共享频道和资源文件的影响。
5. 新写入的宿主/插件日志、历史日志展示和导出都会对常见 URL 凭据、Bearer、Cookie、Authorization、token、password 等字段脱敏。历史日志文件本身不被改写或删除。
6. 服务运行时测试新增停止后本机端口连接被拒绝的断言；模拟器 UI 测试增加日志脱敏与插件导出断言。
7. Python Spider 的常见 `localProxy` 三元组响应现在按 HTTP 响应发送，保留安全的 Content-Type、Range、Content-Range 等头；代理支持 GET/HEAD，HEAD 的长度按来源值传递，GET 按实际内容长度计算。
8. 播放结果校验 HTTP/HTTPS 地址、域名、端口和凭据，限制并清理播放头；也接受常见 `User-Agent$...#Referer$...` 头字符串。无效备用地址不进入结果。
9. 相同操作和完全相同参数的目录/详情请求共用在途结果，不同参数仍隔离；Python Spider 初始化失败只清理本次新载入的资源模块，不影响已有运行实例。
10. 导入带 argparse `--port`、`--bind` 声明的 Python HTTP 脚本时，自动传入服务分配端口与绑定地址；仅在脚本还声明 `--serve` 时添加该参数。静态确认 `/all.m3u` 生成器和路由后，服务启用时自动订阅其本机播放列表。
11. 识别 CatPaw 的 `globalThis.Pans = await ...` ESM Fastify 应用；即使文件内嵌 CommonJS loader 文本，也按 ESM 导入，并在解包副本缺少 `package.json` 时补充 `type: module`。Node 宿主可启动该应用实例并在服务停止时关闭监听。
12. 增加 `WidgetMetadata`、`Widget.http` 和 `loadResource(params)` 解析脚本适配，影视页搜索输出作为结果卡片，详情后可交给现有播放流程；HTTP 桥接限制为 HTTP/HTTPS、15 秒超时和 2 MB 响应。
13. 服务开关改为按服务 ID 管理。Python 宿主维护多份运行任务与独立线程/日志，串行化 Python 顶层初始化，并按服务 ID 停止和等待端口释放；服务页可以同时显示多个活跃会话。Node 宿主改为 session→owner 映射，分别回收定时器、请求、Socket 和监听器，并按会话作用域隔离 CatVod 常用全局对象及 `process.env` 视图。JavaScriptCore router 为每个服务会话创建独立 context、串行队列和网络请求集合。相同端口冲突会明确提示。
14. 增加并发回归：两个 Python HTTP 服务同时监听、分别读取自己的数据目录环境视图，停止一个后另一个继续响应；Node 两会话验证启动/停止和全局/环境视图互不覆盖；为 macOS JavaScriptCore 原生测试增加两个 context 同时运行、单独停止和按服务 ID 清理用例。

## 兼容性与风险

- 未更改公开 M3U 格式、频道标识、订阅 URL、用户偏好键或服务包格式；未删除用户数据。
- 删除订阅与服务仍由用户确认。共享频道在源被移除后，只在没有其他归属时才从频道列表移除。
- 通用 Python HTTP 服务没有统一健康协议时只能显示 HTTP 可达与状态码，不能证明频道清单正确或媒体成功解码。
- 用户启用可识别的 Python HTTP M3U 服务时，应用会添加一个 `127.0.0.1` 订阅 URL；停止服务后订阅保留，用户可在资源页移除。未识别标准路由的 Python 服务仍需手动添加播放列表。
- Widget 桥接仅对影视搜索产生的有限结果建立短期内存映射；脚本或应用重启后需重新搜索。它不代表允许执行远程下载的代码。
- 日志脱敏针对常见凭据字段；无法识别插件任意自定义编码的秘密。历史磁盘日志为避免覆盖用户资料保持原样，但 UI 和导出会先脱敏。
- 当前 App 仍受 iOS 后台执行策略限制；前后台恢复不能保证被系统终止的插件继续运行。
- 多个 Python 服务共用同一个 CPython 解释器和 GIL。宿主隔离 Python `os.environ` 视图、启动参数、会话日志和可跟踪的线程/端口，但无法隔离任意 `sys.modules` 全局状态、C 扩展副作用或脚本自行创建的不可跟踪线程；这不是进程沙箱。Node 会话共用一个 Node Mobile 进程，JSC context 独立但仍共用 App 进程资源。严格互不影响需要每插件独立进程，iOS 当前架构不支持对此作保证。

## 2026-10-24 追加审计

用户要求按服务 ID 独立启停，并继续审计 CCTV、直播与频道页面。本次追加修复：

1. 修正频道分类页搜索和自动线路布尔表达式中的 Objective-C 语法错误；重新检查相邻源码，当前环境仍缺少 Apple SDK，无法替代 Xcode 编译。
2. 频道网格复用既有卡片视图和台标控件；之前每次 `cellForItemAtIndexPath` 都销毁并重建一组子视图。EPG 缓存行只在频道缺少当前摘要时计算。
3. 订阅线路按 M3U `tvg-id` 关联；没有稳定频道 ID 时仅保留本频道线路，不再把相同显示名称的不同频道混作备用源。原始 URL 及其查询参数仍用于订阅和播放。
4. 配置中心按服务 ID 生成运行状态，避免一个 Python 服务的进程状态描述套用到另一个 JS/Node 服务。插件页状态查询也明确使用 `builtin-ysp`。
5. JavaScriptCore 启动超时时继续保留会话 owner，并在后台排入有界停止操作；仅收到停止成功后才释放引用。新增 macOS 原生测试覆盖未完成的异步启动。
6. 播放诊断页读取单次行快照，避免 table view 的行数查询与逐行渲染分别触发动态数据采集。EPG 重新载入后优先保留用户选择日期，日期失效时回到今天或最新日期。

追加验证结果：`python3 -m unittest discover -s Tests -p 'test_*.py'` 共 136 项，112 项通过、24 项因 macOS 原生依赖跳过；`npm test --prefix JSPlugins` 两个测试入口通过；`git diff --check` 通过。新增的 JavaScriptCore 启动超时原生用例随 24 项跳过，需 macOS CI 实际编译和执行。当前仍未测真机并发 3–5 个混合服务同时播放、视频首帧、切台时延、内存和横竖屏大字体布局。

后续验收建议按顺序执行：先由 macOS CI 编译、运行原生 JS/导入/模拟器 smoke 测试；再在目标 iPhone 启动 3–5 个不同 ID 的 Python、Node 和 JSC 服务，分别检测 HTTP 健康及频道清单；随后播放一个频道并逐个停止/重启其他服务，确认当前画面不断流、其余服务状态不变；最后记录冷/热开台、连续快速切台、内存峰值和服务端口释放数据。上述设备数据未取得前，不作“稳定播放已验证”或性能提升百分比承诺。

## 2026-10-24 启停状态补强

- Node 会话现在区分启动请求中、启动应答确认、应答丢失后的状态未知；`activeSessionIdentifiers` 只返回确认启动的会话。状态未知会保留 owner，可继续执行停止；再次启动同一会话会被拒绝，避免重复实例。
- 服务目录增加“启停结果待确认”分组，开关按宿主仍管理该会话显示；关闭、删除、端口占用检查和全局停止都会包含待清理的 Node/JSC 会话。
- Python/Node/JSC 服务状态仍与 HTTP 探测分开。超时或本机接口响应丢失时，界面显示结果待确认；停止没有成功回执时不会删除会话记录。
- 追加验证：`python3 -m unittest discover -s Tests -p 'test_*.py'` 共 138 项，114 项通过、24 项跳过；`npm test --prefix JSPlugins` 通过两个入口；源码契约测试 38 项通过；`git diff --check` 通过。运行环境仍没有 Xcode，因此 NodeMobile/JSC 原生层和模拟器 smoke 尚未编译执行。

## CCTV 节点线路专项调查

见 [CCTV-NODE-ROUTING-DIAGNOSIS.md](Docs/CCTV-NODE-ROUTING-DIAGNOSIS.md)。早期调查确认旧线路菜单实际只是 SDK CDN 偏好流程；该流程不能证明固定播放所选地址。此前偏好配置修正目前仅作为旧设置恢复/诊断辅助，不再是 CCTV 手选线路的播放实现。

本轮用户确认后，CCTV 手选 WS/BD/KS/TX 路径改为将完整 URL（含查询参数）交给 CNPlayer 的 `playLIVEWithUrl:delegate:configOptions:`，自动线路仍按频道 ID 调度。复用 SDK 可取得的 userID、频道统计 ID和 delegate；重试及起播恢复保留所选地址，SDK 拒绝、失败或超时不会静默回退到自动。线路诊断展示所选来源完整地址与 SDK 报告节点，日志只记录主机，避免写入签名查询参数。

`git diff --check` 已通过。本轮没有运行测试或 iOS 构建；当前环境无 Xcode/iOS 运行时。此前报告中的测试通过数属于早期改动，不能视为本轮 URL 接入验证。所选 URL 是否被 SDK 实际接受、许可结果、真机首帧和连续解码均待设备验证。

# build 254 新日志后的改进

本批两份导出共 469 条事件。主会话有 4 次首帧，一次约 7.24 秒进度证据；
一条 play 请求约 18.5 秒后 NO_MEDIA，另一条被取消。没有足以认定新崩溃的记录。

## 代码改动

- NO_MEDIA 归一化失败单独记录 media_play_result_rejected，包含固定字段名、
  返回类型、地址类型和缺失/结构/校验原因；不输出字段值、URL、签名或 Cookie。
  此改动提供定位证据，不伪造有效地址，也不宣称已修复该条来源的提取失败。
- 中继按每次播放解析请求、key/map/media 类型记录首个注册资源的请求、响应头、
  首次读取和完成耗时，最多保留 256 个身份标记；首字节是中继读取观察值。
  切线路即使沿用关联 ID，不同解析请求仍各自记录，并附原始 play request ID。
  开始/完成不能代表解码成功。取消或截断不记录假完成。
- 使用 HTTPResponse.read1 转发当前可用的数据，避免 read(n) 等满固定块。
  内容长度、Range、HLS 清单读取和异常检测保持原语义。HTTP 回归让上游在
  写完首批 64 字节后暂停，确认客户端先收到它们，再释放后续数据。
  宿主响应预算同时覆盖 read/read1，并共享累计计数；混用二者不能重置预算。
  原有单响应上限保留，本轮不放宽插件的下载预算。
- 后续审查发现，媒体中继本身也在插件 HTTP 工作线程内，普通 16 MiB
  累计上限会截断较大的单个视频响应。现在仅中继向播放器转发时的读取
  使用最多 64 KiB 的分块上限，不累计整条流的总字节；普通插件下载和图片
  中继仍沿用 16 MiB 上限。清单仍有 2 MiB 上限，完整性检查和连接超时保留。
- 首页普通重建请求合并 200ms；后台延后渲染。推荐轮播、分类书架、继续观看和收藏按
  内容、来源/站点、宽度、主题、字体大小复用视图。固定来源仍按原
  实现重建，不能称为整页已完成增量化。手动刷新会清除模块复用记录。
- 海报连续三个同 origin 的网络超时触发 60 秒退避，之后最多一个半开探测；
  成功响应清除超时计数。HTTP 492 不计为网络超时。仅在有新图片需求时探测，
  不为不可见图片新增后台定时请求；同 URL 请求仍合并，其他域不受影响。

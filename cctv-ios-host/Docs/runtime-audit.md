# Python、Node.js 与 JavaScriptCore 运行时审计

本文记录 CCTVHost 当前三类脚本运行时的边界和本次修复。运行时状态、HTTP 健康检查、频道清单和视频解码是不同阶段；代码或测试通过不代表任意导入脚本都能播放。

## 运行模型

| 运行时 | 当前模型 | 已有保护 |
| --- | --- | --- |
| Python | App 内单个 CPython 解释器；每个服务有独立会话、入口线程和数据目录，服务初始化串行化 | HTTP 服务及工作线程跟踪、协作停止、线程池上限、请求/客户端超时、端口关闭确认 |
| Node.js | App 内单个 Node.js Mobile 实例；会话按服务 ID 跟踪，共享 Node 事件循环 | 会话作用域全局变量、定时器/套接字/监听器跟踪、宿主 HTTP 桥请求/响应限制、插件句柄清理 |
| JavaScriptCore | 每个服务会话创建独立 JSContext 和串行队列 | 请求、响应、并发和定时器上限；停止时取消网络请求、释放上下文；启动超时后保留会话直到有序清理 |

三者都运行在 CCTVHost App 进程内，服务 ID 是生命周期边界，不是操作系统安全边界。Python 模块缓存和解释器状态仍为进程共享；Node 服务共用一个事件循环。脚本若执行不返回的同步死循环，宿主无法像独立子进程那样强制终止它；Node 的同步死循环还会阻塞同一 Node 实例中的其他服务。此边界需要在产品状态和支持说明中保持明确。

## 本次修复

- Python 服务在等待其他脚本完成串行初始化时收到停止请求，之前仍可能在稍后执行入口。运行时现在在执行 `runpy` 前重新检查停止状态，并在取消时释放启动门闩。
- Python 插件此前可无界创建工作线程。现在单服务最多 48 个、宿主最多 128 个活跃的受跟踪线程；HTTP 请求工作线程仍受每服务信号量限制。
- Python 原生服务启动请求之前就显示为运行中，且自然退出的任务对象会留在任务表。现在只有解释器会话准备后才报告运行中，退出任务从活跃表清理，失败原因保留到重试/停止或有界淘汰。
- Node HTTP 桥在 HEAD/204 等无响应体情况下会异常。现在将无响应体视作空内容；请求超时输入被限制在 1–20 秒范围，协议桥仅接受格式有效、无 URL 凭据的 HTTP/HTTPS 地址。
- Node 未处理的 Promise 异常此前只有日志，插件仍可继续接收调用。现在按异步会话归属将该插件标记为失败并清理其受管理句柄，其他会话可继续使用。
- Node 停止钩子可能无限等待或抛错后遗留监听端口。现在限制钩子等待时间，失败后清理由宿主管理的监听、连接、流和定时器，并检查端口是否确实关闭；仍在监听时保留会话供重试。
- 服务启动失败或确认停止后，Python、Node、JavaScriptCore 的按服务日志回调都会清除；日志文本本身仍由现有脱敏与容量上限机制处理。
- UI smoke 曾依赖可变的远端 CatPaw 脚本及旧固定散列，远端更新会令模拟器检查在运行前失败。现在从同一仓库构建本地包，并校验构建生成的散列。

## 回归与验收边界

本次本地回归覆盖 Python 启动取消、线程数上限、独立服务停止；Node 空响应、Promise 异常隔离、关闭钩子失败后的端口释放；以及服务日志回调的生命周期源码契约。JavaScriptCore 的现有请求限制和停止路径需要在 macOS 原生测试/模拟器构建中继续验证。

当前 Linux 工作区没有 Xcode、iOS SDK 或真机，因此 Objective-C/iOS 构建、Node.js Mobile 真机运行、JavaScriptCore 真机运行、内存压力以及真实视频解码均需在 macOS CI 或设备上验收。不能据此报告 iPhone 上“绝不崩溃”或“所有影视源均可播放”。

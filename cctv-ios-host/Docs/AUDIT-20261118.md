### 2.3 播放器生命周期与播放所有权（“切换页面后仍在播放”的代码与产品语义判定）
- **单会话播放所有权 (`PlaybackCoordinator.m`)**：全局维护唯一的 `currentSession`（`RootViewController` 直播会话或 `MediaPlaybackViewController` 点播会话）。当新会话调用 `claimSession:` 时，自动暂停旧会话。
- **“切换页面后仍在播放”的代码真相与产品语义**：
  1. **顶层 Tab 切换（CCTV Tab 0 / 频道 Tab 1 切换到 影视 Tab 2 / 资源 Tab 3 / 设置 Tab 4）**：`RootViewController.m:254` (`switchToTab:`) 在 `tab >= 2` 时显式调用 `[self suspendLivePlaybackForReason:@"switched_to_non_live_tab"]`，立即停止直播播放器并记录挂起状态，切回直播 Tab 时按需恢复。
  2. **从直播 Tab 压栈进入子页面（如节目单、设置子页、资源详情）**：`RootViewController.m:410` (`navigationController:willShowViewController:`) 在 `viewController != self && self.activeTab < 2` 时调用 `[self suspendLivePlaybackForReason:@"left_live_navigation_page"]` 暂停直播。
  3. **影视详情页内嵌播放与全屏点播退出**：
     - 全屏点播页 `MediaPlaybackViewController.m:417` (`viewWillDisappear:`) 在检测到控制器或父容器被 pop/dismiss 时，若未处于系统画中画（`!self.pip.isPictureInPictureActive`），立即调用 `[self teardownAfterScreenExit]` 停止 `AVPlayer`、销毁 `MediaPlaybackCicadaAdapter`、取消 `HLSRouteProbe` 与隐藏网页嗅探 `WKWebView`。
     - 详情页顶部内嵌播放器 `MediaDetailViewController` 在返回上级页面（`goBack` / `viewDidDisappear:`）时调用 `[self teardownInlinePlayback]` 销毁内嵌播放器。
  4. **退到系统后台 (`onBackground`)**：
     - 点播页：除非开启了“后台自动画中画”（`autoPiP`）且 `AVPictureInPictureController` 已激活，否则 `pauseForBackground` 会暂停点播。
     - 直播页：当用户停留在可见的直播页（`activeTab < 2 && topViewController == self && !presentedViewController`）锁屏或切后台时，因 `Info.plist` 声明了 `UIBackgroundModes = [audio]` 且 `onBackground`（`RootViewController.m:487-506`）有意保留当前直播实例不调用 `resignActive`，从而支持**直播后台听音 / 自动画中画**；若用户已离开直播页再切后台，则已在离开页面时被挂起。
- **四阶段播放状态严格区分**：
  1. **播放请求已发出**：`native_playback_start_requested` / `media_playback_start_requested`（仅代表调用开始，UI 显示“连接中”与 `spinner`）。
  2. **播放器报告 playing**：`AVPlayer.rate > 0` 或 `CNPlayer playBackStateDidChanged:1`。
  3. **媒体项 ready**：`AVPlayerItemStatusReadyToPlay`（触发 `playback_item_ready`）或 `CNPlayer loadStateDidChanged:4` (`PrepareDone`) / `CicadaPlayer EventPrepared`。
  4. **视频已出首帧**：`AVPlayerLayer.readyForDisplay == YES`、`CicadaPlayer EventFirstFrameRendered (3)` 或 `CNPlayer statEvent == 3`（触发 `playback_first_frame`，此时才隐藏加载指示器、停止起播超时看门狗并记录首帧耗时）。

### 2.4 Cicada / FFmpeg 崩溃取证分析（结合 `.ips` 与符号栈）
- **证据文件**：`cctv-ios-host/Docs/CICADA-FFMPEG-CRASH-INVESTIGATION.md` 及真机崩溃日志 `CCTVHost-2026-04-16-225852.ips`（设备 `iPhone15,3`，iOS `26.4 23E246`）。
- **崩溃现场**：
  - 异常类型：`EXC_BAD_ACCESS (SIGSEGV)`，`KERN_INVALID_ADDRESS at 0x0000000000000000`。
  - 崩溃线程：Thread 32 (`Cicada::demuxer_service` 异步解复用线程)。
  - 调用栈回溯：
    1. `CicadaPlayerSDK + 0xd0e9c`：`Cicada::demuxer_service::open_callback(void*, char const*, int, std::__1::map<...> const&, void**)`
    2. `CicadaPlayerSDK + 0xc9748`：`Cicada::demuxer_service::createDemuxer(Cicada::IDemuxer::type)`
    3. `CicadaPlayerSDK + 0xcae64`：`Cicada::demuxer_service::initOpen(bool)`
    4. `CicadaPlayerSDK + 0xd7fb8`：`Cicada::ffmpegDataSource::Open(int)`
    5. `alivcffmpeg + 0x2084b4`：`av_Thread`
  - 同时 Thread 35 正在执行 `alivcffmpeg read_data` -> `ffurl_read_complete` 读取 HLS 分片。
- **根因与边界判定**：
  - 根因位于闭源二进制 `CicadaPlayerSDK.framework` 内部：当 HLS 主清单包含多路子流（如独立音轨/字幕轨 `#EXT-X-MEDIA`）或在 `prepare` 尚未完成时发生并发 `start`/`stop`/销毁，Cicada 的 `demuxer_service::open_callback` 在创建子流数据源时对空指针解引用。
  - **宿主缓解措施（已落地于源码）**：
    1. `MediaPlaybackDecodeRouter.m` 默认将标准 HLS/MP4 优先交给系统 `AVPlayer`（硬解稳健），仅在 FLV/MKV/裸 TS、MPEG-DASH、扩展名缺失且嗅探为非原生容器、或 `AVPlayer` 失败回退时才启用 `CicadaPlayer`。
    2. `MediaPlaybackCicadaAdapter.m` 取消 `autoPlay`，严格等待 `CicadaPlayerEventPrepared (1)` 到达且 `generation` 匹配后才调用 `start`；销毁时通过 `CicadaSchedulePlayerDestruction` 先置空 `delegate`、调用 `stop` 并延迟 `350ms` 再调用 `destroy`，给后台 `av_Thread` 留出退出窗口。
  - **未验收边界**：因 `CicadaPlayerSDK.framework` 无源码，宿主层无法修改 `0xd0e9c` 处的空指针检查；必须在 iOS 真机上针对多音轨 HLS、快速切集与弱网断流场景做压力回归验证，不能仅凭静态测试宣称该崩溃已根除。

#### [P0-1] 本机 `/_cctvhost/host-fetch` 桥接在异常时关闭 TLS 证书校验（`CERT_NONE`），并将用户请求 URL 泄露给第三方公共代理，且跨源重定向未剥离敏感凭据

- **受影响模块**：本机媒体服务 HTTPS 桥接（`Plugins/media-service.py`）
- **文件路径与行号**：`cctv-ios-host/Plugins/media-service.py:511-571`
- **复现步骤或触发条件**：
  1. JSC 或 Node 插件通过本机 `/_cctvhost/host-fetch` 发起 HTTPS 请求；
  2. 当目标站点连接超时、TLS 握手失败或遇到网络抖动抛出非 `HTTPError` 异常时：
     - 原第 513 行立即创建 `unverified_ctx = ssl._create_unverified_context()`（即 `CERT_NONE`）并携带原请求全部 `Cookie` / `Authorization` 头重发请求；
     - 若仍失败且为 `GET` 请求，原第 529–548 行将完整目标 `url`（含查询参数、签名 token）拼接到第三方公共代理 `https://api.codetabs.com/v1/proxy?quest=...` 与 `https://api.allorigins.win/raw?url=...` 并通过 `unverified_ctx` 发送；
     - 当 `followRedirects=True` 且发生跨域名 301/302 重定向时，原第 554–571 行将原请求的 `Cookie` 和 `Authorization` 原封不动转发给新域名，且未拦截 `https://` -> `http://` 降级重定向。
- **用户可观察到的症状与根因**：
  - 根因：历史兼容兜底代码直接关闭了 TLS 校验并引入了外部公共 CORS 代理，不仅违反了设置页隐私声明（`SettingsViewController.m:383`：“只保存在本机，不会上传到任何服务器”），还使插件请求暴露于中间人攻击（MITM）和第三方代理日志窃取之下。
- **证据来源**：源码静态审计（`Plugins/media-service.py:511-571`）+ 单元回归测试（`Tests/test_round17_full_audit_fixes.py`）。

- **修复内容与验收标准**：
  - 已移除 `ssl._create_unverified_context()` 及 `api.codetabs.com` / `api.allorigins.win` 第三方代理调用；
  - 仅在遇到缺失中间 CA 证书（`_is_missing_intermediate_ca_error`）时，复用经过根证书链校验的 `_resolve_aia_opener_for_host`；
  - 在 `followRedirects` 循环中强制要求 `https` 协议，并在跨源（scheme/host/port 变化）重定向时剥离 `Authorization`、`Proxy-Authorization` 与 `Cookie` 请求头。

#### [P0-2] `MediaRelay` 的 AIA 中间证书补全逻辑将未验证的对端叶子证书注入信任存储并开启 `VERIFY_X509_PARTIAL_CHAIN`，导致 PKI 证书链校验被绕过；`ysp-live.py` 存在未验证 SSL 分支
- **严重级别**：P0（安全 / TLS 信任链绕过）
- **受影响模块**：媒体流本机中继（`Plugins/host_media_relay.py`）与央视频直播服务（`Plugins/ysp-live.py`）
- **文件路径与行号**：`cctv-ios-host/Plugins/host_media_relay.py:415-425`、`cctv-ios-host/Plugins/ysp-live.py:751-757`
- **复现步骤或触发条件**：
  1. 当上游 HTTPS 媒体服务器返回 `SSLCertVerificationError(20, "unable to get local issuer certificate")`（例如服务器未下发中间证书，或攻击者伪造了未知签发者的自签/中间人叶子证书）时，`host_media_relay._open_with_timeout_retry` 调用 `_resolve_aia_opener_for_host(hostname, port)`；
  2. 原第 415 行执行了 `pem_blocks.append(ssl.DER_cert_to_PEM_cert(der_cert))`（将从对端直接读取、未经验证的叶子证书 `der_cert` 放入信任锚点列表），并在第 419–421 行设置了 `ctx.verify_flags |= ssl.VERIFY_X509_PARTIAL_CHAIN` 后调用 `ctx.load_verify_locations(cadata='\n'.join(pem_blocks))`。
- **用户可观察到的症状与根因**：
  - 根因：在 OpenSSL 中，`X509_V_FLAG_PARTIAL_CHAIN` 允许将信任存储中的任意非根证书（包括叶子证书本身）直接视为信任锚点（Trust Anchor）。把对端刚发来的叶子证书 `der_cert` 加入 `load_verify_locations` 并开启 `VERIFY_X509_PARTIAL_CHAIN`，会导致即使 `pem_blocks` 没有获取到任何 AIA 中间证书，或者中间人伪造了任意触发 `verify_code == 20` 的假证书，OpenSSL 都会因为“叶子证书等于信任存储中的叶子证书”而直接判定验证通过！此外，`Plugins/ysp-live.py:754` 仍保留了 `ssl._create_unverified_context()` 分支。
- **证据来源**：源码静态审计（`Plugins/host_media_relay.py:415-425`、`Plugins/ysp-live.py:751-757`）+ 单元回归测试（`Tests/test_round17_full_audit_fixes.py`）。

### 3.2 架构边界与潜在风险（需知悉边界，不以破坏现有功能的方式强改）

#### [R-1 / P2 潜在风险] 商业视频页面 URL 自动回退第三方解析接口与公共苹果 CMS 资源站（隐私与错片风险）
- **位置**：`Sources/MediaPlaybackViewController.m:1590-1672` (`MediaPlaybackResolveVIPNativeStream`)、`Plugins/csp_adapter.py:516-743` (`resolve_maccms_stream_by_title`, `resolve_vip_url_via_parsers`, `resolve_vip_watch_url`)、`Plugins/host_media_runtime.py:1478-1509, 1807-1840`。
- **现象与机制**：当影视源返回优酷/腾讯/爱奇艺/芒果 TV 官方网页地址或 `parse=1` 时，宿主与 Python 运行时会自动向硬编码的第三方解析接口（如 `zy.qiaoji8.com`）及 6–8 个第三方苹果 CMS 采集站（如 `caiji.dyttzyapi.com`、`bfzyapi.com`、`ffzyapi.com` 等）发起按片名搜索与选集匹配。
- **风险与边界说明**：
  1. 会将当前观看的商业视频网页 URL 或影片标题发送给上述第三方站点；
  2. 按片名子串匹配采集站在同名剧集、多季剧集或综艺期数不一致时存在“播错片/串集”的固有风险；
  3. 现有测试套件（`Tests/test_comprehensive_audit_fixes.py:156-208`、`Tests/test_round5_audit_fixes.py:85-93`）明确断言了该机制的存在，因此按审计规则第 2/3 条保留该功能，在此明确记录其隐私与内容匹配边界。建议后续在设置页提供显式开关（默认仅使用合集自身声明的 `parses` 解析器，用户开启后再允许回退公共采集站）。

#### [R-2 / P1 供应商二进制边界] `CicadaPlayerSDK.framework` 内部 `demuxer_service::open_callback` (`0xd0e9c`) 空指针崩溃边界
- **位置**：`Frameworks/CicadaPlayerSDK.framework/CicadaPlayerSDK` (`0xd0e9c`)、`Sources/MediaPlaybackCicadaAdapter.m`。
- **风险与边界说明**：详见 2.4 节。宿主已通过 `MediaPlaybackDecodeRouter` 默认优先 `AVPlayer`、`EventPrepared` 门控 `start`、以及延迟 350ms 销毁（`CicadaSchedulePlayerDestruction`）做最大程度隔离，但二进制内部缺陷无法在无源码情况下彻底修补。

#### [R-3 / P2 运行时隔离边界] 内嵌 CPython 单解释器与 Node.js Mobile 单实例并发边界
- **位置**：`Sources/PyHost.m`、`Scripts/host_service_runtime.py`、`Sources/NodePluginRuntime.m`、`Plugins/node-plugin-host.cjs`。
- **现象与机制**：
  - **Python**：iOS 端使用单进程内嵌 CPython 3.13 解释器（全局 GIL），由 `Scripts/host_service_runtime.py` 的 `ServiceEntry` 通过线程本地路由（`_ThreadRouter` 隔离 `stdout`/`stderr`、`_EnvironProxy` 隔离 `os.environ`、`_ChdirRouter` 隔离工作目录、快照恢复 `sys.modules`/`sys.path`、跟踪清理线程/Socket/Timer）实现按 `service_id` 隔离。但若两个 Python 服务同时加载依赖全局状态的 C 扩展模块，或用户编写的脚本在未响应 `stopping` 事件的死循环中持续占用 GIL，仍可能互相影响。
  - **Node.js Mobile**：`NodeMobile.framework` 在进程生命周期内只能调用一次 `node_start`（`NodePluginRuntime.m`），所有 Node 插件服务共享同一个 Node.js 事件循环进程，由 `Plugins/node-plugin-host.cjs` 通过 `vm.createContext` 沙盒、独立 HTTP 端口和按 `service_id` 跟踪的 `sockets`/`timers`/`AbortController` 隔离。若某个 Node 插件执行同步 CPU 死循环（如恶意的 `while(true){}`），会阻塞整个 Node 线程。

### 5.2 iOS 端性能设计与待真机测量方法
源码中已落地的性能优化与防卡顿机制（静态确认）：
1. **启动与首屏可交互时间**：`RootViewController.m:534` (`restoreDiagnosticLog`) 将最大 4 MiB 的日志文件读取与脱敏移至后台 `QOS_CLASS_UTILITY` 队列，仅截取末尾 256 KiB 回主线程；`ProfileStore.m` 将超大 `cachedChannels` 载荷（`_hasDiskPayload`）卸载到独立磁盘文件按需读取，避免阻塞 `NSUserDefaults`。
2. **列表滚动与图片加载**：`MediaFeedPosterCell` 与 `MediaEntryListCell` 启用 `layer.drawsAsynchronously = YES`；`HostImageLoader` 限制单域名并发、在后台串口队列使用 `CGImageSourceCreateThumbnailAtIndex` (`kCGImageSourceShouldCacheImmediately`) 解码缩略图并缓存至 `NSCachesDirectory/CCTVHostImageThumbnails`；`RootViewController+Catalog.m` 在列表拖拽/减速期间暂停 EPG 与遥测探测，待 `scrollViewDidEndDecelerating:` 后仅探测可见行。
3. **待真机实测方法**：在 iPhone 真机上开启“设置 -> 运行诊断”，执行冷启动、500+ 频道列表快速滚动、连续切台 20 次、点播切集 10 次后，导出 `RuntimeDiagnostics` JSONL 会话报告（包含 `app_launch_finished`、`media_grid_first_cell_will_display`、`playback_first_frame` 的 `elapsed_ms` 以及 `task_vm_info.phys_footprint` 峰值物理内存 `peak_footprint_bytes`）与 MetricKit `MXDiagnosticPayload` 进行定量验收。

### 5.3 隐私脱敏与可观测性审计
- **日志与诊断脱敏 (`HostLogRedactor.m` & `RuntimeDiagnostics.m`)**：
  - `HostLogRedactor` 自动抹除 URL 用户密码（`://***:***@`）、敏感查询参数（`token`/`key`/`auth`/`sign`/`signature`/`wsSecret`/`txSecret`/`pass`/`password`/`cookie`/`session`/`uid`/`guid`/`access_token`）、Xtream 路径凭据及 `Bearer` / `Cookie` / `tvg-id` 敏感值。
  - `RuntimeDiagnostics` 采用字段白名单（`AllowedKeys`），将每个会话文件限制在 `512 KiB`（最多保留 12 个历史会话，总计 `<= 6 MiB`），将运行日志 `cctvhost.log` 限制在 `512 KiB` 滚动截断（保留末尾 `256 KiB`），无过量写盘风险。

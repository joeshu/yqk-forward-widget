# 央视官网订阅：APTV 多频道与 CCTV-2 电脑版

使用 [央视官网直播](https://tv.cctv.com/live/) 对应的播放来源：APTV 手机版现提供 14 个已通过真实分片验证的频道，原 Python + Node 电脑版继续仅提供 CCTV-2。本服务独立于 `ysp-live`，不会替换成央视频或其他平台的来源。

**APTV 手机实验版现已独立提供：[cctv-aptv.py](https://raw.githubusercontent.com/joeshu/yqk-forward-widget/main/cctv-native/cctv-aptv.py)。** 用户 iPhone 日志已确认 Python 3.14.6 可以直接调用系统 JavaScriptCore 并执行微型 WASM。新版本使用该引擎，不依赖 Node、npm、浏览器、FFmpeg 或子进程；已在 Linux JavaScriptCore 中通过真实央视分片处理及连续解码验证，**用户已确认关闭 MitM 后可在 iPhone APTV 播放**。详见 [APTV 验证记录](APTV-VALIDATION.md)。原有 `cctv-native.py` 仍用于电脑/服务器，需要 Node。


所有相关文件现集中在本目录：

| `cctv-aptv.py` | APTV 手机直接加载的单文件入口 |

APTV 原远程链接若指向仓库根目录，请改为本目录的新链接后重新加载；本地订阅地址不变。

在 APTV 添加 Python 服务，远程链接填写上面的 `cctv-aptv.py`，加载最新代码并启动，然后订阅：

```text
http://127.0.0.1:18768/all.m3u
```

APTV 版提供下列 14 个频道，来源仍为央视官网；电脑版仅提供 CCTV-2。若运行设置更改端口，订阅中的端口也要对应更改。服务会立即监听；默认在 GET 订阅时提前准备频道（`--no-warmup` 可关闭），校验并载入随脚本携带的固定版本官方组件，默认仅在内存缓存，不访问用户主目录、无需磁盘写入权限或 `--setup`。可选 `--cache-dir` 才启用磁盘缓存，缓存读写失败自动退回内存。查看 `http://127.0.0.1:18768/status` 可区分初始化、取源、就绪或错误；`official-runtime-download-permission-denied` 表示下载操作被拒绝，区别于磁盘缓存问题；`jscore-framework-or-time-limit-unavailable` 表示所需系统接口不全，不能据微型测试通过推断完整服务一定可用。初次播放需要等待组件及相邻分片准备，本次 Linux 连续测试约 19.6 秒进入就绪；不保证手机同等速度。

`aptv-jscore-probe.py` 是独立诊断脚本，现默认监听 `18770/status`，避免 APTV 将“打印后正常退出”显示为启动失败。`--once` 可恢复仅打印行为。诊断脚本不提供频道，请使用新播放服务的链接。

最新稳定性处理：若官方调度返回的地址未通过 HTTPS/CDN 校验，拒绝访问该地址，并最多重新向官方取源两次；不再因第一次地址拒绝立即结束频道。`/status` 的 `last_source_rejection` 记录最近被拒绝地址的域名和协议，不含播放签名。若持续失败，需要根据这些信息核实 CDN，当前不会自动放行未知域名。`official-playback-not-permitted` 表示官方接口明确拒播，不属于播放器缓冲，重试策略不绕过该许可检查。

根据手机 14:15Z 日志，补充官方调度实际返回的完整网宿域名 `ldocctvwbcdcnc.v.wscdns.com`，不放行其他网宿子域名。HTTPS、证书、端口和跳转校验继续执行，避免这条已知地址被本地校验拒绝后重新取源。开发网络本轮未调度到该节点，实际手机媒体播放仍需验证。

TS 重组进一步减少逐包分配，只更新长度不变的包负载，保留原包头和适配区；需要缩短负载的包仍走完整重组。内部包视图使用不可变轻量元组，填充调整完成后停止多余循环。最终输出仍完整校验。同片交替测量 20 轮，重组 CPU 中位耗时从 15.006 毫秒降至 13.252 毫秒，输出逐字节一致，这只反映开发机重组部分。

新增 `segment-timing` 日志与 `/status.last_segment_timing`：分别显示下载等待、所有者线程分析、官方组件处理、TS 重组的墙钟秒数。并行预解析发生在下载线程，因此 `owner_analysis` 可接近 0，下载等待可能含等待预解析完成的时间。只记录首两片日志；过旧缓存重新准备时也记录。恢复缓存后使用 `cache-media-ready` 报告实际恢复耗时，避免重复显示最初启动耗时。见 [CDN 与逐包优化验证](CDN-PACKET-VALIDATION.json)。

默认并行准备还包括分片首次 TS 解析，可与官方组件初始化、原生媒体处理重叠；相邻分片的边界证明复用同一字节对象的解析，避免重复解析输入。仍需两个完整处理分片才发布播放清单，输出会重新解析验证。不能保证每个网络下固定秒数切台；可用 `--no-parallel-prepare` 恢复串行准备。

### 新增的 14 个官网频道

APTV 新版仍订阅同一个 `/all.m3u`，更新脚本后要在播放器中**刷新订阅**，才会从原先 1 个更新为 14 个。包括 CCTV-1、2、4、7、9、10、11、12、13、14、15、17，以及 CCTV-4 欧洲、美洲。网页中的 `cctvjilu` 对应 CCTV-9，`cctvchild` 对应 CCTV-14；其他频道使用官网原标识，不切换央视频源。

实测 20 个官网入口，以上 14 个取得官方许可和媒体清单，逐台下载真实原始分片、通过原 SDK 处理并对完整样本严格解码，均为零错误；本轮样本均是 1280×720 H.264。CCTV-3、5、5+、6、8、16 本次返回 `play != 1`，未加入订阅。详见 [逐台验证记录](CHANNEL-VALIDATION.json)，不保证不同时间、网络或节目状态下持续可用。CCTV-2 已由用户在 iPhone 验收，多频道换台还需该手机验证。

手机端按需准备当前选中的频道，订阅刷新仅在尚无当前频道时预热 CCTV-2，不会初始化全部频道，也不会打断正在看的其他台。换台后默认暂停并短时保留最近一个已就绪频道，15 秒内切回可复用原组件；最多两个原生处理实例，选择第三个频道时淘汰更早的一台。未就绪频道直接停止，不堆积初始化任务。它主要面向单设备逐台观看，不提供同时独立观看所有频道的能力。当前状态与当前频道见 `/status`。

最近频道缓存默认开启，无需额外设置。只保留最近一台的最后两个已校验分片；分片最后发布距今不超过 8 秒、且不超过这两片总时长时，可以立即返回清单。超过这个新鲜度时清空分片、更换代际，再用原组件处理当前直播窗口，避免继续播放过旧缓存。组件保留超时后由原工作线程释放，切回走正常启动。可用 `--recent-channel-seconds 0` 关闭，或设置 1～30 秒；保留分片可能增加少量直播滞后。`/status` 的 `cache_hits`、`cache_buffer_hits`、`resume_ready_seconds` 可区分组件复用和分片直接命中。

CPU 优化只省去输出校验中不会使用的字节映射，TS/PES/NAL 检查和精确视频字节核对继续执行。同一真实分片在开发机上交替测量 20 轮，重组 CPU 中位耗时从 26.7 毫秒降至 18.4 毫秒，输出逐字节一致；这不是手机整次加载提速比例。一次真实 A→B→A 测试中，A 切回的首清单为 0.0031 秒；B 的旧分片超时，复用组件重新准备为 1.524 秒，两次随后各严格解码 16 秒无错误。只是开发网络短样本，不保证每次或手机同速，详见 [CPU 与缓存验证](CPU-CACHE-VALIDATION.json)。

借鉴用户提供的 `ysp-engine.js` 连接管理，现默认复用上游 HTTPS 连接及已验证的 TLS 上下文，减少同一来源重复建连。只复用已完整读完的响应；空闲连接最多保留 6 条，超过 15 秒不再复用；代理路由、CONNECT 目标、TLS 策略或代理凭据不同会使用独立连接。复用的 GET 连接被上游关闭时最多换新连接重试一次，证书失败继续报错。保留系统代理、证书/域名验证、来源检查和原视频处理逻辑。可用 `--no-http-reuse` 关闭，`/status` 的 `http_connections` 显示池的创建/复用次数。

与最近频道缓存一起实测，切回 CCTV-2、CCTV-4 的首清单为 0.0023 / 0.0017 秒，随后分别严格解码 16 秒无错误。四轮冷启动对比均解码通过，但网络波动较大，尚不能据此推断稳定的首播提速。见 [连接复用验证](HTTP-REUSE-VALIDATION.json) 和 [参考实现分析](REFERENCE-REVIEW.md)。

进一步的启动优化：记住本次进程中已经成功的 TLS 1.2 取源方式，下次取源或换台优先复用；网络改变导致握手失败时可尝试默认 TLS 恢复。仅保留一次经验证成功的选择，不保存账号、地址或签名，不关闭证书校验，仍不能替代关闭相关域名的 MitM。每轮只预取最多 3 个相邻分片，减少过量排队以及换台时旧频道的收尾等待。


**需要 Python 3.10+、Node.js 20+ 和 npm，不需要 Chromium、Playwright 或 FFmpeg。** Python 提供本地订阅和分片缓存，Node 运行固定版本的官方组件；处理后的原 TS 分片直接供播放器解码，不采集网页画面、不重新编码。这仍是 Python + Node 程序，只有纯 Python 的环境不能运行。


### APTV 适配实现

手机服务复用已有 TS 映射、同源调度、播放许可检查、缓存、重试和 HTTP 逻辑。Python 通过系统 C API 执行原样官方 JS/WASM；使用原 Emscripten `instantiateWasm` 接口同步实例化，网络与定时器由 Python 驱动，存储使用固定版本 fake-indexeddb。原始官方组件下载后校验 SHA-256，不写入仓库，不替换来源。全部 JavaScriptCore 操作由同一工作线程执行，原生执行时间限制终止失控脚本，不创建 Python 原生回调。

第三方 fake-indexeddb 6.2.6 的原始 CommonJS 内容和本地加载器随单文件打包，Apache-2.0 许可完整保留在 [vendor/fake-indexeddb-LICENSE](vendor/fake-indexeddb-LICENSE) 以及单文件 `THIRD_PARTY_LICENSE` 中。该依赖只是浏览器存储接口，不是新的节目源。

构建：`python cctv-native/build_aptv.py`；检查：`python cctv-native/build_aptv.py --check`。iOS 运行不安装任何 pip/npm 包。Linux 开发验证可通过隐藏参数 `--jscore-library /绝对路径/libjavascriptcoregtk-4.1.so.0` 指定测试系统库，这不属于手机安装要求。


## 下载与启动

下载本目录的单文件 [cctv-native.py](https://raw.githubusercontent.com/joeshu/yqk-forward-widget/refs/heads/main/cctv-native/cctv-native.py)，保存到本地。无需同时下载本目录的源码。

首次安装独立运行依赖：

```sh
python cctv-native.py --setup
```

该命令通过 npm 安装四个固定版本依赖，并下载原样的官方 `live.worker.js`，校验 SHA-256 后存入 `~/.cache/cctv-native`。依赖使用独立缓存目录，官方组件不写入仓库；下载到不同版本时会报错，需要更新脚本。安装和播放均沿用系统代理与 TLS 校验。

之后启动：

```sh
python cctv-native.py 18768 --warmup
```

播放器添加订阅：

```text
http://127.0.0.1:18768/all.m3u
```

`--warmup` 在播放器 GET 订阅时后台提前取源，订阅本身立即返回；省略时首次选台才启动。HEAD 不触发预热。首次播放需要等待官方组件初始化及相邻分片准备，真实耗时见 [VALIDATION.md](VALIDATION.md)。

手机或电视访问电脑上的服务时：

```sh
python cctv-native.py 18768 --bind 0.0.0.0 --warmup
```

订阅地址改为 `http://电脑局域网IP:18768/all.m3u`。手机上的 `127.0.0.1` 指向手机自身。旧版 `cctv-web.py` 也默认使用 18768，两个服务需停止其中一个，或用不同端口启动。

## 状态与运行选项

- 单台地址：`http://127.0.0.1:18768/cctv2.m3u8`。
- 状态地址：`http://127.0.0.1:18768/status`。包含实际阶段、分片数量、缓存占用、阶段耗时与脱敏错误；`transport_retries` 是本次会话的网络重试次数，`last_transport_error` 在恢复后清空；`media_ready` 不代表用户播放器已经验收通过。
- `--node /路径/node`：指定 Node 可执行文件。
- `--cache-dir /路径/缓存目录`：改变安装缓存；安装与启动须使用同一目录。
- `--buffer-mb 64`：分片内存上限，范围 16–256MiB；最多保存 10 个分片，播放器列表提供最近 6 个。
- `--idle-timeout 120`：无人观看后停止取源，范围 30–3600 秒。再次选台会重新初始化。

多个观众共享一份取源与处理进程。播放请求最长等待约 50 秒；尚未准备好或失败返回 HTTP 503，可查看 `/status`，错误冷却 30 秒后由新播放请求重试。旧会话或已淘汰分片返回 410，需让播放器刷新清单。

短暂超时、断链及 HTTP 408 / 429 / 5xx 会按 0.8–4 秒退避重试，保留已就绪的播放缓存；401 / 403 / 404 会重新获取官方调度。重试受无媒体进展 30 秒的检查预算约束，当前网络读取结束后判断；持续故障仍会停止。官方拒绝播放、格式错误和组件进程错误不会进入网络重试循环。

主清单首次解析后直接轮询媒体清单，120 秒取源刷新时重新解析，减少重复请求。该优化不保证固定的冷启动耗时。

## 当前支持范围

本版仅支持当前观察到的 TS / H.264 分片结构。为确认分片末尾的媒体单元完整，先核对相邻 HLS 序号及下一片起始码，再按原 TS 结构重组媒体数据、保留原音频和时间戳。支持的变短媒体单元限于单个 PES 内；增长、未知封装、无法证明相邻帧边界或上游格式变化都会明确失败。下载过慢导致直播窗口跳过片段时，丢弃缺失区间并用 HLS 不连续标记重新接入当前窗口；`/status` 的 `source_gaps` 记录次数，不拼接缺失片段的媒体字节。它不具备通用媒体转码能力。

上游返回 `play != 1` 时停止，不通过更换地区、账号或来源继续取流。官方组件和接口变化、网络及播放器差异都可能影响可用性；目前不保证其他网络可播，电脑版未提供其他频道、EPG、回看或 4K；APTV 版的频道及节目单见本文前述说明。真实验证范围以 [VALIDATION.md](VALIDATION.md) 为准。

此前的 [cctv-web 浏览器采集版](../cctv-web/README.md) 继续保留，可独立选择使用。

## 开发

编辑 `service.py`、`cctv_native_ts.py`、`engine.cjs`，然后生成单文件：

```sh
python cctv-native/build_service.py
```

离线检查：

```sh
python -m unittest discover -s cctv-native/tests -v
python cctv-native/build_service.py --check
node --check cctv-native/engine.cjs
python -m py_compile cctv-native/cctv-native.py cctv-native/cctv-aptv.py cctv-native/service.py cctv-native/cctv_native_ts.py cctv-native/build_service.py
```

CI 运行 Python 3.10 / 3.12 与 Node 22 的离线检查，不执行官方接口实播。FFmpeg 可用于开发时验证输出解码，服务运行不依赖它。

取流停滞排查：`source-media-stalled` 表示播放器初始化已完成，但 30 秒内没有发布新分片，不直接说明原因。新版日志打印首次进入的 `phase`、每次网络重试的 `operation/cause`，出错时自动打印脱敏 `diagnostics` JSON；`/status` 同时提供 `operation`、`operation_seconds`、`playlist_entries` 和 `last_segment_bytes`。`media-playlist` 指清单获取，`segment-download` 指分片下载，`sdk-transform` 指原组件处理。诊断不输出上游地址、签名、异常原文或证书内容，仍保留原来的超时保护。

若 `source-api` 出现 `URLError:SSLError`，新版只为该官方 API 增加一次保留证书与主机名校验的 TLS 1.2 兼容重试，其他媒体请求不套用这项协议限制。日志同时显示 OpenSSL 的枚举原因，便于进一步区分握手故障；证书验证失败不会触发兼容重试。手机该故障尚待新版实测，不保证 TLS 1.2 一定解决。

加载耗时说明：手机成功播放后的日志显示，初始 SSL 失败重试仍可占用约 13 秒。应先关闭针对央视域名的 MitM，再重启服务和选台，避免把握手失败耗时算作播放器缓冲。新版本默认在读取订阅时预热，并减少 TS 映射索引构建、列表切片和重复解析；保留相邻片边界证明与输出一致性检查。首次清单就绪会打印 `media-ready startup_seconds=...`，该数值从本次后台准备开始计算，不包含播放器自身缓冲。

### 手机数据传递与后续扩台核验

新版在系统支持时使用 JavaScriptCore 的公开 TypedArray C API 复制视频媒体缓冲区，减少逐字节 Base64 与字符串转换；日志显示 `media-transfer=typed-array`，`/status` 的 `media_transfer` 同步报告。系统无相应符号时仍使用原 Base64 路径。复制的只是提交给处理器的视频媒体，不读取或修改 SDK 内部内存。原组件、网络许可检查及输出校验均保留。

TS 解析结果会绑定同一不可变原始分片，供重组复用；不同字节对象或未证明末尾边界时拒绝复用，输出仍重新解析核对。明确的旧式 TLS 握手失败仅前两次采用 0.15/0.30 秒短退避，此后仍用原有退避及无媒体进展保护，该退避策略本身不改变 TLS 配置。它能减少部分本地处理与重试等待，不保证手机固定几秒换台。

继续核对了[官网旧频道目录](https://tv.cctv.com/new/live/cctv/)的 6 个入口，共累计核对 26 个标识。5 个新增候选被官方接口拒绝；旧英语新闻入口虽返回视频，但新页面的 `rel_url=cctv9` 实际已映射到中文 CCTV-9 纪录，核验解码画面后作为重复排除。因此目前仍是 14 个独立频道，不按页面旧名称虚增数量。逐项证据见 [CHANNEL-VALIDATION.json](CHANNEL-VALIDATION.json)。

### 明确旧服务器握手错误的兼容

手机最新日志显示已启用 TypedArray，但取源仍反复出现 `UNSAFE_LEGACY_RENEGOTIATION_DISABLED`。仅在该官方 API 的标准 TLS 与 TLS 1.2 均失败、最后错误明确为此枚举时，新版才使用 Python/OpenSSL 的 `OP_LEGACY_SERVER_CONNECT` 兼容旧服务器；它会接受未提供安全重协商扩展的旧服务端，因此这是一项限定范围的握手兼容，不是完全不改变 TLS 行为。证书链、主机名验证和 TLS 1.2 最低版本保留，同时设置 `OP_NO_RENEGOTIATION` 禁止后续重协商。

兼容范围严格限制为 `vdnx.live.cntv.cn/api/v3/vdn/live`，该配置下不跟随其他域名或路径的重定向；不会用于 SDK 下载或媒体分片，不启用全局关闭证书验证、不更换官方来源。成功后仅在内存记住此模式；`/status` 显示 `source_api_tls=TLSv1.2-legacy-server`。可用 `--no-legacy-source-tls` 关闭此兼容；缺少相关 OpenSSL 标志的旧 Python 保留原重试行为。

依据：[Python SSL 选项文档](https://docs.python.org/3/library/ssl.html#ssl.OP_LEGACY_SERVER_CONNECT)。本地通过人为注入前两次同类握手失败，第三次使用真实官方接口验证成功；开发网络代理与手机实际网络不同，仍需新版手机实测。

换台取消也已补全：旧频道完成当前下载/SDK 步骤后检查停止状态，不再继续做已无观众需要的 TS 重组和发布，减少与新频道争用手机 CPU。

### 并行准备首播

APTV 默认将组件初始化与取源、媒体清单、最多 3 个首批分片的准备重叠执行。下载结果直接复用，不重复下载；网络许可检查通过前不下载媒体，所有 SDK 调用仍在其所属线程执行。可用 `--no-parallel-prepare` 关闭。日志 `source-preparation=parallel` 及 `/status` 的 `parallel_preparation` 用于确认模式；`preparation_phase` 记录首批准备所在步骤。电脑版默认继续串行。

若组件初始化过慢，使预取清单已超过 8 秒，会重新获取清单，不以过时直播窗口强行开播。初始准备失败仍走原有重试/拒绝逻辑；换台或初始化失败会取消后续准备，已开始的网络读取仍受超时限制。首播仍要求原先的两片就绪与相邻边界证明。

本地四次网络实测见 [STARTUP-VALIDATION.json](STARTUP-VALIDATION.json)：并行约 5.7/6.3 秒取得首个可播清单，串行约 6.4/12.2 秒，四次各严格解码 8 秒均无错误。样本小、存在网络与预热波动，不据此推断手机固定提速比例。

新增首播观察点：`playlist_requested` 是播放器请求清单的时间；`playlist_available` 是首次向该请求提供可用清单的时间；`first_media_requested` 是播放器首次请求有效媒体分片的时间，均相对本次后台准备开始计算。它们不代表画面已经显示。与 `ready` 对照，可区分后台准备耗时、用户选台时间及播放器取片前等待；HEAD 探测不记录这些指标，后续清单轮询不覆盖首次时间。


2026-10-20 首播前瞻与原生初始化优化：APTV 默认开启 `--prefix-lookahead`。第三个输入分片先请求前 128 KiB，只在 PAT/PMT、完整首个视频 PES、相邻序号与连续流边界均可验证时用于证明第二片结尾；前两片仍完整下载、处理、重组后才发布。前缀永不作为播放分片。CDN 忽略 Range 时复用完整响应；范围或边界不符合要求时自动下载整片。第三片完整下载在前两片下载结束后与 SDK 处理重叠，并核对总长度和全部前缀字节；变化时重新取官方源。可用 `--no-prefix-lookahead` 对照。该方式减少首播关键路径下载量，后续完整第三片仍需下载，因此总流量可能多约 128 KiB。

原生 WASM 装载改为 Python 解码后复制同一份已校验字节，减少 JS 循环和无用返回值字符串转换，保留 Promise 微任务执行边界。开发机十轮组件初始化中位数 0.173→0.129 秒，约降低 25%，不代表手机整体提速。相同 CCTV-12 分片六轮交替测试（每模式三轮，排除取源/清单时间）首清单中位数 3.060→1.714 秒，每轮严格解码零错误；样本较小。另六轮完整直播首次启动为 3.018–10.107 秒，网络波动下未证明整体冷启动收益。169 项测试通过，含 11 项真实 JavaScriptCore 测试；手机效果仍需新版日志确认。详见 [PREFIX-STARTUP-VALIDATION.json](PREFIX-STARTUP-VALIDATION.json)。


2026-10-20 完整输入解析继续减少 CPU 分配：服务保留已验证的 TS 包用于 PES 重组，跳过该流程不消费的逐字节位置映射。通用映射 API 默认行为不变；PAT/PMT CRC、连续计数、PES/NAL、相邻边界与重组后完整解析校验仍执行，不修改官方 SDK。三片真实 CCTV-2 录制分片使用同一官方 SDK 输出做交替对比，每模式每片 20 轮：解析加重组 CPU 中位数分别 32.013→23.169、24.883→17.845、49.571→34.000 毫秒，降低约 28%–31%；单轮峰值 Python 分配减少约 11%。输出逐字节一致且严格解码零错误。15 份已保存频道布局（包含一份历史重复频道）验证媒体和重组结果一致；不是新增可播频道。171 项测试通过，含 11 项真实 JSC 测试。这是开发机处理环节收益，不能推算为手机整体开台加速百分比。结果见 [PACKET-INPUT-VALIDATION.json](PACKET-INPUT-VALIDATION.json)。

本轮新版 CCTV-2、CCTV-12 各连续严格解码 16 秒零错误，处理均继续至第 5 片，无缺片或网络重试。首清单分别 7.702 / 5.312 秒，进一步说明整体等待仍受取源与网络主导，不能用上述 CPU 百分比估算开台耗时。


### APTV 节目单

新版 `/all.m3u` 自动声明 `http://127.0.0.1:18768/epg.xml`，节目 ID 与订阅中的 14 个频道完全对应，包括 CCTV-9 纪录、少儿、欧洲和美洲频道。更新单文件、重启原服务并刷新订阅后即可使用；若 APTV 没有自动关联，在节目单设置手动填写上述地址。自定义端口或局域网访问时，按实际订阅主机和端口填写。

数据来自央视官方 `api.cntv.cn/epg/epginfo`，按北京时间输出昨天、今天、明天实际返回的节目及起止时间，不生成回看链接。每个日期一次批量查询全部频道，共三次请求；优先发布今天，其他日期在后台补齐。订阅返回不等待节目单，也不因此启动视频。正常缓存 15 分钟，北京时间跨日立即触发刷新；后台刷新期间可继续读缓存，缺失/请求失败 30 秒后允许重试，失败保留仍在日期窗口内的成功数据。上游明确返回空数组时保留空节目，不拿其他频道填充。首次请求尚未取得任何节目时可能返回 503，可稍后重试；`HEAD` 不取源。`/status` 中 `epg` 提供节目数量、缺失频道及脱敏刷新错误。

开发网络实测：14 个频道均有节目，三日共 1,341 条，全部 `+0800`；缓存 XML 响应约 2 毫秒，播放器实际展示仍需手机确认。测量见 [EPG-VALIDATION.json](EPG-VALIDATION.json)。


2026-10-21 单片首播实验：经用户同意，APTV 默认 `--startup-segments 1`，在第一片完整视频已下载、经官方组件处理、重组并通过完整校验后即可返回 HLS 清单；下一片仍须证明第一片末尾边界，绝不发布未完成的 NAL 或边界前缀。后续片继续原后台流程，媒体清单保持直播、滚动更新。桌面版仍默认两片；`--startup-segments 2` 恢复此前的首播缓冲门槛。`/status.startup_segments` 显示当前设置，缓存切回的新鲜度判定继续要求两片，不扩大缓存有效期。

单片清单可以减少服务端等待，但 APTV/AVPlayer 可能自行等待更多分片才出画面；不能把首清单耗时等同于手机首帧。减少启动缓冲也减少了对短时网络抖动的余量，若出现刚打开就停顿，可切回两片。开发网络与播放器验收结果见 [SINGLE-STARTUP-VALIDATION.json](SINGLE-STARTUP-VALIDATION.json)，手机实际首帧及长时间播放仍待用户验证。

### 六路最近频道缓存（2026-10-21）

APTV 默认 `--channel-cache-size 6`，包含当前频道与最多 5 个最近频道。只在实际观看后缓存，不预启动全部频道；后台组件暂停视频处理，原始分片预取由下述独立策略控制，切到第 7 路时按最近使用顺序淘汰最旧的一路。`--recent-channel-seconds` 默认改为 60，支持 0–180；0 关闭组件保留。到期、淘汰或关闭时清空缓存视频，并由所属线程释放组件；原生上下文总数受同一上限控制。

单片首播继续生效，切回缓存时也允许复用一片完整新鲜视频。新鲜度上限仍为 8 秒且不超过已缓存视频总时长；旧分片不会因为组件保留 60 秒就继续播放。新鲜时直接使用原有媒体窗口，过期时复用原组件、清空旧窗口并准备当前直播。每个后台频道最多保留最近两片，不能保证六路随时瞬间出画面。`/status` 增加 `channel_cache_size`、`retained_channel_count`、`cached_media_bytes`，并继续提供缓存命中、分片新鲜度和恢复耗时。

开发机六路顺序首次选台为 5.126 / 1.884 / 1.464 / 1.818 / 1.290 / 1.285 秒，切回第一和第六路（分片已过新鲜期）首清单 2.730 / 1.463 秒，均未重新初始化原生组件，各严格解码 16 秒零错误，并处理到第 6 片。这不是同条件速度对比，也不是手机首帧测量。六路缓存时开发机整个进程 RSS 约 267 MiB，切回后约 289 MiB；媒体缓存约 4.6 MiB，其余包含 SDK、JS 引擎和进程开销。组件关闭后 RSS 仍约 259 MiB，分配器并不保证立即归还全部内存；不能据此保证 iOS 内存表现。手机若内存紧张，可设 `--channel-cache-size 2` 降低保留数量，或缩短保留时间。185 项测试通过，包含七路轮换保持最多六个组件、所属线程关闭和单片缓存复用。记录见 [SIX-CACHE-VALIDATION.json](SIX-CACHE-VALIDATION.json)。


### 快速切台任务清理与网络恢复（2026-10-21）

频道暂停、淘汰、到期或服务退出时，现在统一取消尚未执行的组件准备/分片下载任务。每个任务执行前还会检查频道状态，避免已经切走的频道继续发起排队请求；完成或失败后立即移除任务追踪引用。已经开始的网络请求仍受原有超时限制，不跨线程关闭连接。正常恢复、切回、后续分片均保持原来的许可检查和完整视频校验。失败的整片升级任务也从重试缓存中清理。

`source-media-stalled` 及已识别的临时网络错误退出后，允许再次启动的冷却由 30 秒缩短为 3 秒。只有播放器再次请求且原工作线程已退出才会重新启动，不保证三秒内恢复画面；官网明确不允许播放、媒体格式不支持及其他错误仍保留 30 秒冷却。`/status` 增加 `pending_input_tasks` 与 `retry_after_seconds`，便于区分排队工作和冷却等待。

在六路缓存配置下，开发网络对两个真实央视频道连续来回切换 20 次，新鲜缓存首清单约 0.6–1.4 毫秒，最终频道继续生成新分片并严格解码 16 秒零错误。此数据只反映服务端缓存清单响应，不是 APTV 首帧，不代表这次修改带来同等提速。关闭后追踪任务数为零。191 项回归测试通过，含 11 项真实 JSC；新测试覆盖排队下载取消、运行中请求正常收尾、恢复后可继续提交新工作、任务引用清理和错误分类冷却。见 [SWITCH-RECOVERY-VALIDATION.json](SWITCH-RECOVERY-VALIDATION.json)。

追加验证：另一次 20 次快速切台后连续严格解码 90 秒，生成至第 23 片，零解码错误、无缺片或传输重试；后台缓存在 60 秒到期后正常释放，当前频道继续播放，服务关闭后追踪任务数为零。这是有限时长的开发机测试，不代表长期或手机稳定性保证。


### 修复官方组件更新导致全台初始化失败（2026-10-21）

手机日志四次选台均在 `engine-initialization` 报 `response-too-large`，未处理任何视频。官方可变地址 `live.worker.js` 从原 2,344,162 字节更新为 4,871,689 字节，触及旧 4 MiB 限制且摘要不同。临时放大上限、校验新版摘要并适配其压缩变量名后，新版可以初始化但产生 H.264 解码错误，因此没有直接采用新版。

当前单文件内固定携带此前已验证、仍能处理当前直播的原版官方组件，可逆压缩后约 472 KB；脚本约 795 KB。加载先限长解压、校验完整 SHA-256，组件损坏则拒绝执行，不下载可变地址尝试替换；不改写官方 JS/WASM。默认只使用内存，继续符合 APTV 单文件方式。电脑版生成文件的安装步骤也使用同一固定资产。来源及版本见 [vendor/CCTV-RUNTIME.md](vendor/CCTV-RUNTIME.md)。官方配置接口、取源和媒体依然需要正常网络与原有许可验证。

### 最近频道原始分片预取与媒体缓存预算（2026-10-21）

默认 `--recent-prefetch 1`：对最近观看后暂停的 1 个频道，单独使用一个网络线程预取当前清单和两片相邻完整原始视频，后台组件保持暂停。当前频道至少已有两片且输出新鲜时才启动预取；不会提前启动没看过的台。每轮结束后至少等待 4 秒，连续相同序号/地址复用已下载字节，官方播放许可最长 30 秒重新检查。预取网络请求单次超时 4 秒；失败后冷却 30 秒，错误不会使正在播放的频道失败。可设为 `0` 关闭或 `2` 预取最近两台，仍使用一个串行网络线程。

切回时，已完成且清单准备时间距今不超过 6 秒的预取交给原线程处理，并继续执行原来的 TS/PES/NAL、相邻边界与重组输出完整校验。预取不发布视频、不调用 SDK，也不把未完成前缀作为播放分片。切台会使旧预取失效；已经开始的网络读取仍可能到超时才结束，后续请求停止，迟到结果不写回。无新鲜预取时回到普通准备流程。

默认 `--cache-memory-mb 32`，支持 16–256 MiB。预算统计已保存的播放分片和待用原始预取数据；清理过期数据后，按最近使用顺序丢弃较旧后台媒体数据，保护当前播放。单台输出缓冲也不超过该预算。原生组件/JavaScriptCore 内存、在途下载及 Python 对象开销另计，因此它不是整个进程的内存硬上限；六路组件上限仍由 `--channel-cache-size` 控制。`/status` 增加 `accounted_cache_bytes`、`media_cache_budget_bytes`、`budget_evictions`、`prefetch_hits` 和 `recent_prefetch` 的字节/复用/失败计数，诊断不输出上游地址。

开发机两轮独立实测，视频缓存已过期后切回 CCTV-2：关闭预取首清单 1.4885 秒，开启并命中预取 0.1632 秒；每轮前台 CCTV-4、切回 CCTV-2 各连续严格解码 16 秒零错误。不是同分片控制实验，也不是 APTV 首帧测量，不据此承诺固定提速。开启轮切回前，预取额外下载 3,455,064 字节、复用一片；保持预取会增加流量和耗电，移动网络可设 `--recent-prefetch 0`。

追加开启预取的 75 秒前台严格解码：零错误、19 片、无缺片或传输重试；采样到媒体缓存最大 11,262,140 字节（约 10.7 MiB），低于 32 MiB 预算；后台频道 60 秒到期后媒体数据清零，预取线程关闭正常。204 项测试通过（11 项真实 JSC），手机实际首帧、耗电和长期表现待验收。记录见 [RECENT-PREFETCH-VALIDATION.json](RECENT-PREFETCH-VALIDATION.json)。

后续启动路径梳理：冷启动与最近频道预取现在选择清单中最新的一组连续分片；最新位置遇到断点时，退到最近能证明边界的连续组。这样可以避免先下载窗口中较旧、之后会被丢弃的分片。预取刷新只保留序号和完整 URL 都相同的原片，其余旧数据会在下载新片前释放，减少瞬时内存占用。该改动尚无手机首帧和内存实测数据。

# 用户参考附件的提速思路

参考文件为用户提供的 `ysp-engine.js` 和 `ysp-live-v9.5.py`。后续再次上传的 Python 文件 SHA-256 与前一份相同。两份参考实现的取源协议不同于本项目当前 `tv.cctv.com/live/` 来源，因此迁移通用缓存与连接管理，保留现有官方许可检查及原组件视频处理。

| 参考位置 | 实际作用 | 当前项目处理 |
| --- | --- | --- |
| JS 227～240 行 `httpsAgent/httpAgent` | keepAlive，复用同目标连接 | 新增标准库 HTTPS 连接池和验证后的 TLS 上下文复用，保留系统代理 |
| JS 291～301、426 行 `playlistCache` | 将改写后的播放清单缓存 30 秒 | 当前继续生成滚动清单，复用有新鲜度限制的视频分片；避免清单长期停在同一窗口 |
| JS 459～490 行 `/segment` | 下载并直接返回媒体字节 | 本项目的官网媒体仍经过原官方组件处理和 TS 校验；参考转发速度不能直接作为本项目首播速度 |
| Python 2514 行 `coalesce_refresh` | 同一频道的重复刷新合并 | 当前 `Channel.demand` 在条件锁内保护唯一工作线程，已有同类行为 |
| Python 2554 行 `TsSegmentCache` | 对完整下载分片做容量和过期限制 | 当前保留有界 ring，另有最近一个频道 15 秒组件缓存、新鲜分片复用 |
| Python 999、1309～1318 行 | 同一设备会话关联多个频道，空闲释放配额 | 借鉴按需与淘汰；手机版服务继续限制最多两个原生处理实例 |

## “8 路”的含义

附件 `--links-per-device` 的默认值是 6，可通过参数或 `YSP_LINKS_PER_DEVICE` 配成 8。`linked_channels` 是该协议会话关联的频道集合，超过本地配额时先清理空闲链接；`LINK_IDLE_TIMEOUT` 为 15 秒。这不表示同时初始化八个视频处理引擎，也不是八个分片下载线程。

参考文件还将高码率请求延后到选台停留一段时间后，再后台升级；默认 `--zap-debounce` 为 10 秒。该流程依赖另一套来源的基础流与高码率流，本项目当前来源没有因此自动获得一条可直接转发的基础流。

当前连接池的“最多 6 条”只限制空闲连接数量，不是频道配额。连接请求独占借用；完整读完后才能归还。代理路由、CONNECT 目标、代理凭据摘要及 TLS 策略构成复用边界。新鲜度、原生实例数和空闲连接数分别管理。

验证见 [HTTP-REUSE-VALIDATION.json](HTTP-REUSE-VALIDATION.json)。开发机对比证明复用生效、解码通过，但网络样本不能证明稳定首播提速或 iPhone 同速。

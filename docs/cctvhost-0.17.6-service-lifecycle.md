# CCTVHost 0.17.6：Python 服务切换与起播停滞

截图中的两条提示对应不同限制：导入脚本没有专用停止回调时无法关闭；原宿主只允许每个 App 进程执行一次脚本。0.17.5 解决了主线程停止导致的卡死，但没有解决这两个兼容性问题。

0.17.6 保留单一 CPython 解释器，改为逐个运行服务会话。不会调用 Py_Finalize 或通过异步异常强制杀线程。只有旧会话的主脚本、跟踪到的 Python 工作线程、清理任务和服务监听全部退出后，才能运行下一份脚本。点击另一个服务的开关会先停止当前服务，成功后启动目标服务；停止失败时保留真实状态。

## 支持的停止方式

标准库 HTTPServer、ThreadingHTTPServer 及常见 socketserver 子类由宿主自动记录，未提供停止回调也可以关闭。会话中的 threading.Thread 会继承所属服务；线程化服务最多同时处理 12 个连接。无显式超时的已接收连接设置 10 秒超时。停止时中断这些客户端连接，避免半截 HTTP 请求阻塞服务退出。

自定义后台循环应提供协作式停止回调：

```python
import builtins
import threading

stopping = threading.Event()
builtins._cctvhost_stop_service = stopping.set

# 业务循环使用 stopping.wait(timeout)，并在返回 True 时退出。
```

兼容内置插件的 `_ysp_stop_server`。回调不必返回 True；实际资源退出才是停止成功的依据。回调只启动一次，等待有期限；超时可再次检查停止状态。未退出的普通任务、原生扩展线程、绕过 threading 创建的线程、第三方事件循环或主动改变标准库生命周期机制的脚本，不承诺支持自动切换。宿主不会把这些脚本伪报为安全停止。

会话启动时同步 `YSP_DATA_DIR`、`CCTVHOST_DATA_DIR` 和 `CCTVHOST_PORT`。脚本仍须使用配置端口实际监听；宿主会记录真实监听地址，并对端口不一致给出日志提示。不会把旧端口订阅静默改写到其他服务。已完成会话会移除它注册的退出回调和专用停止回调，并恢复脚本搜索路径，避免保留旧模块命名空间。普通 import 的模块仍共享同一个解释器，这不是进程隔离。

## 启动时的反向 DNS

macOS 的真实内置插件集成测试捕获了启动停滞：HTTPServer.server_bind → socket.getfqdn。等待 8 秒时仍在解析自己的监听地址，并未进入服务循环。宿主管理的 HTTP 服务直接使用绑定地址设置 server_name 和 server_port，省去本地代理不需要的反向 DNS。

这证明了 macOS 测试中的停滞原因；手机日志没有对应 Python 线程栈，不能据此断言其全部服务就绪超时都由 DNS 引起。

## 原生播放器恢复

新日志中 CCTV-5/5+ 多次 VDN 成功后没有 setup，原先会一直等待到 25 秒。新增一次受限恢复：总等待至少 8 秒、VDN 成功后至少 6 秒、仍未 setup/首帧且无明确播放错误时，丢弃旧包装实例并用新实例重试。恢复次数按用户选台限制为一次；切台后旧实例回调被代次和实例检查过滤。首帧耗时保留从最初选台开始计时。

已经 setup 的正常缓冲、鉴权/版权失败和时移播放不走这条恢复路径。日志中其他原生频道约 7–10 秒的正常首帧耗时尚未证明有改善；实际 SDK 不支持当前起播缓冲设置时仍保留 SDK 默认值。

## 验证

新增用例覆盖无回调 HTTP 停止及同端口重启、主脚本返回但后台服务器仍运行、返回 None 的停止回调、阻塞回调超时及去重、不可协作线程阻止替换、未运行监听器关闭、环境更新、半截 HTTP 请求、反向 DNS 不可用，以及真实内置 YSP Live 在同一解释器内连续启动和停止两次。集成测试使用 --no-4k，不访问云端，不能据此声称设备注册或真实频道流已验证。

原生 Foundation 检查验证恢复触发窗口、只重试一次、错误与 setup 后不重试。模拟器中的 SDK 和 Python 宿主仍为替身；真机须重点验证“导入服务 → YSP Live → 导入服务”切换、连续启停、长时间播放与 CCTV-5/5+。

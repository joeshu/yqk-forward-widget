# APTV iOS 实机卡顿与原生后端调查（2026-10-22）

## 结论

用户在 APTV TestFlight **9.9.9（548）** 中运行 v0.3.7，设备探针识别为 iPhone 12（`iPhone13,2`）、iOS、64 位。播放日志显示每段约 4 秒的视频需要约 4–10.5 秒完成 SDK 处理，服务无法持续追上直播输入。这与“播放几秒后停一下”吻合。

耗时集中在 SDK 处理调用中：分片排队为 0 秒，TS 映射与校验约 0.02–0.06 秒，SDK 单段耗时约 4.00–10.54 秒。该计时包含 JavaScriptCore/WebAssembly 桥接和被模拟 SDK 的处理，目前日志没有进一步区分每一部分。CCTV-1 两段处理耗时分别为 9.41 秒和 10.80 秒（SDK 分别为 9.20 秒和 10.54 秒），共更新两段用了 25.89 秒。降低清晰度不是本轮方案；加大缓存或更换 CDN 不能提高这段串行 SDK 运算的持续吞吐，只能暂时延后缓冲耗尽。

## iPhone 探针观察

- 已加载组件包含 Apple 的 AVFoundation、CoreMedia、VideoToolbox 与 JavaScriptCore。
- 本进程未观察到名字匹配央视/kooplayer 的已加载组件，也未观察到 Unicorn C API；`start(ctx)` 没有收到宿主对象。
- JavaScriptCore C 接口可见，但这只证明系统 JSC 可调用。系统播放器框架、JSC 符号和 Python 脚本服务都不等于可用的 iOS 央视 DRM SDK 或原生插件接口。
- 这些结果只描述探针运行当时已加载的组件与可见符号，不能证明 APTV 包内绝无未加载组件，也不能推断正式授权或播放兼容性。

因此，本轮仍没有获得能替代 ARM 模拟器的原生后端。Android `libkooplayer` 仍不能直接作为 iOS 动态库加载。日志把瓶颈定位在 SDK 执行链，但没有细到证明全部耗时都是 ARM 模拟指令。要从根本上解决，需央视/授权 SDK 提供当前服务兼容的 iOS ARM64 SDK及集成材料，或由 APTV TestFlight 宿主提供可编译、签名调用该 SDK 的正式插件/桥接 ABI。单靠 Python 缓存、线程数或 CDN 切换无法把这段串行处理速度提升到实时。

APTV 官方通知对 9.9.9（540）的公开说明是新增 Python/PHP 脚本服务；用户截图确认本机是后续的 9.9.9（548）。公开说明没有列出原生插件 ABI。该版本中的探针也没有收到宿主 `ctx` 对象，因此当前脚本入口没有可调用的原生桥接面。版本号及功能说明不能证明 App 内没有未加载的框架，但它没有提供可据此集成的原生接口。

| CCTV-2 百度 | 4.48–5.72 秒 | 4.37–5.58 秒 | 4.00–4.12 秒 |

上游线路之间确有波动，但各路线仍经过同一 SDK 执行引擎；即使换到网络更快的线路，也不会消除主要的本地计算耗时。

## 下一步

当前生产单文件保持 v0.3.7，不做可能增加直播延迟的缓冲默认值修改。APTV 版本/构建已确认是 9.9.9（548）；继续原生集成需要取得可核验的 iOS SDK、头文件、授权/兼容说明及宿主插件接口。

已有独立的官方网页来源服务可以作为另一条来源分别验证；它与央视影音 App UDRM 不是同一协议/来源，本报告没有把它切换成当前 App 订阅，也没有将网页路径说成已修复本问题。

APTV版本功能依据：[官方通知频道的 TestFlight 9.9.9（540）发布说明](https://t.me/s/aptvplayerchannel)，该说明列出 Python/PHP 脚本服务。用户截图提供实际 9.9.9（548）构建号。

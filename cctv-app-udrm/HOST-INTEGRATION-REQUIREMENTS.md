# 原生宿主集成需要确认的接口

这是研究接口清单，不是已经存在的APTV API，也不是让用户提取App二进制或许可密钥。

用户随后提供的 IPA 已完成只读元数据核对：有独立 iOS ARM64 CNPlayerSDK，前端有 UIView/回调及直播生命周期；Cicada 依赖有官方公开头文件，CNPlayerSDK 正式合同仍未获得。具体证据与收窄后的需求见 [IOS-SDK-IPA-REVIEW.md](IOS-SDK-IPA-REVIEW.md)。此前探针的ctx缺失只描述一次调用，不能排除其他宿主模块/全局；iOS正确嵌入签名的framework可以设计加载接口，不能将运行时加载概括为一律不可用。

## 宿主能力

- APTV是否提供官方原生插件/SDK集成入口，支持iOS ARM64、哪些最低系统版本、由谁编译签名与分发。
- Python如何调用受支持的宿主接口，调用线程、对象生命周期、取消与内存限制。
- 是否允许随宿主打包已签名的C/C++运行时及WASM AOT产物；不假设可以运行时下载并加载未集成dylib。
- 播放器是否支持所需系统DRM的完整流程。只支持M3U URL不代表支持任意DRM SDK。

## 官方SDK能力

- 提供方确认的iOS SDK、版本、头文件、示例、授权范围、支持的频道/画质与设备绑定方式。
- SDK输出是播放视图、受保护样本、压缩媒体还是其他对象；不能预设输出明文TS。
- 如果仅提供原生视图，需要APTV嵌入播放器；此时本地M3U代理架构也需调整。
- 如官方提供直接HLS或FairPlay路径，需确认源站授权与宿主支持，不改标签冒充兼容。

## 最小可评审验证

先验证宿主调用返回版本/能力，不下载媒体；再验证正式许可和单频道播放。随后比较同画质下首帧、持续吞吐、CPU、峰值RSS及后台恢复，保留当前实现作对照。退出、取消、失效许可和网络失败必须有明确错误并释放资源；不得把运行层就绪误报为许可或播放已成功。
